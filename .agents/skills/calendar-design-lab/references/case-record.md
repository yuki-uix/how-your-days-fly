# Retain a design case without inventing its outcome

Use a local case record for substantial multi-turn design work, selected-design revisions or replay. A simple factual answer does not need one. Reuse existing experiment/recipe records when they already serve the task; do not silently migrate or overwrite them. This is a small recording convention, not a website backend or a universal rendering contract.

## Start and inspect

From the repository root:

```sh
python3 .agents/skills/calendar-design-lab/scripts/design_case.py new \
  --id books-weekly --request '我想要书籍主题的周历。'
python3 .agents/skills/calendar-design-lab/scripts/design_case.py check \
  output/cases/books-weekly/record.json
```

The default location is ignored `output/cases/<id>/record.json`. The initializer refuses to overwrite an existing record. It retains the request but leaves every interpretation unknown; the agent supplies interpretations using the actual conversation. No calendar, user preference, selected direction or approval is generated by this helper.

Before a first small study, record only the meaningful confirmed constraints, provisional choices, direction hypothesis and resulting artifact paths. Initialized nulls and empty histories can stay as they are. Expand the record when selecting or revising a direction; creating a detailed dossier is not a prerequisite to useful visual work.

Keep real requests, personal books, uploads and feedback local until their sharing scope has been reviewed. The public [book-weekly example](../examples/book-weekly.json) is synthetic, with proposed directions and no rendered design or user approval. It is a usage example, not a personal brief or tested aesthetic result.

## Decisions and directions

`brief` contains view, use, theme, theme role, period, sequence, medium, dimensions, language, week start and visual preferences. Each decision has:

```json
{"value": null, "basis": "unknown", "evidence": []}
```

Use `user-stated` or `user-confirmed` only with scoped evidence from the person's words. `default` is an explicit editable working choice; `hypothesis` is an interpretation to explore; `verified-fact` needs a calculation or source. Unknown fields remain null and do not block an exploratory draft. A Chinese input alone does not establish the final calendar's language, dimensions or preferred type.

`mode` records discuss/create/revise/replay; `case_kind` distinguishes real from synthetic; `phase` is a descriptive work marker, not an approval gate. Store selected high-information questions in `questions` when useful. Do not ask questions that context has already answered.

For each `direction`, use a unique `id`, title, hypothesis, a compact design card and linked structure/rule/material IDs as useful. `status: proposed` with no artifacts is only a proposal. Use `rendered` only after actual output exists, has been inspected and is retained as a preview/export artifact. A source image is not the rendered calendar.

`selection` uses the same value/basis/evidence convention. Its value is a list of direction IDs, allowing mixed choices. A system-recommended direction remains a hypothesis until the user selects it. Selection of an idea does not approve the later detailed output.

## Revisions, evidence and file identity

Keep a stable revision ID and parent, the change request, `keep`, `change`, unresolved interpretation and actual artifacts. Create a new revision for changes; do not replace the retained files of an earlier accepted version.

An illustrative revision shape:

```json
{
  "id": "r2",
  "parent_revision": "r1",
  "change_request": "Increase the notes area while keeping the date columns.",
  "keep": ["date-column relationship"],
  "change": ["notes-area allocation"],
  "artifacts": [],
  "technical_review": {"status": "not-run", "evidence": []},
  "user_review": {"status": "pending", "evidence": []}
}
```

The snippet is a record shape, not an implemented revision. Actual artifacts have `role`, path relative to the record directory, and SHA-256. Once files exist, generate their identities with:

```sh
python3 .agents/skills/calendar-design-lab/scripts/design_case.py fingerprint \
  --base output/cases/books-weekly --role source \
  output/cases/books-weekly/r2-layout.svg
```

Insert the returned entries into the appropriate artifacts list; repeat for previews, date data, selected assets or exports. Save editable text/layout and exact fonts/assets as well as outlined proofs. Do not rely on a remote URL or prompt to preserve the chosen design. The helper reads files but never executes recorded renderer commands.

Technical review uses not-run/partial/passed/failed. User review uses not-requested/pending/feedback/approved/rejected. A passed/approved/rejected outcome requires evidence and `revision_id` matching the reviewed revision. Approval of r1 cannot simply be copied onto r2. A user's request to retain a relationship belongs in `keep`; it does not approve all of r2.

When ready to retain a recipe, reference its revision and record the actual entry point, supported inputs, selected artifact identities and replay evidence using [recipe.md](recipe.md). Draft recipes are allowed. A replay status of passed requires actual run/output evidence, independent of user review. Do not claim change-of-year or change-of-week support unless run and inspected.

## What a check establishes

`check` catches missing decision evidence, broken direction/revision references, approval attached to the wrong revision, missing retained files and changed hashes. It allows unanswered design questions and untested work to remain explicitly unresolved. It cannot establish whether recorded user words are authentic, whether date calculations or content are correct, whether an image may be redistributed, whether a render was truly executed, or whether the design works for a person. Inspect those with [review.md](review.md) and record the actual evidence.

Use `learning` for scoped observations, candidate rules, recurring implementation problems and links to supporting cases. Apply the promotion guidance in [design-exploration.md](design-exploration.md); neither a case count nor a successful JSON check turns an observation into a general design rule.
