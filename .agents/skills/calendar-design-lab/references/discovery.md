# From a request to a usable design brief

Use this reference when a calendar request leaves important choices open. The outcome is enough shared understanding to make the next useful design move; a complete questionnaire is not required. Use the [design atlas](../../../../docs/design-atlas.md) for existing structures, rules, studies and material candidates.

## Identify the requested mode

- **Discuss or research:** explain interpretations, capabilities and tradeoffs. A hypothetical example is not authorization to start its design, collect a personal book list or interview the user.
- **Create or revise:** use available context, choose the next meaningful question or visual study, and continue the authorized work.
- **Preserve or replay:** reopen the existing brief, decisions and assets. Carry forward confirmed choices instead of interviewing again.

Keep the mode explicit in the case record. Building this skill does not itself start a real customer's calendar case.

## Keep the origin of each decision

| State | What it means | How to use it |
| --- | --- | --- |
| Fact | A verifiable date, file property, source claim or implementation capability | Keep its source or calculation; do not confuse a source claim with a user's taste |
| User-confirmed | An explicit requirement or choice supported by the user's words | Preserve its scope; “keep these date columns” does not confirm the whole design |
| System default | A stated provisional choice that makes progress possible | Make it visible and editable; using it does not make it user-confirmed |
| Hypothesis | A proposed interpretation or design relationship | Test it with an example, comparison or targeted question |
| Unknown | No adequate evidence yet | Ask only when it changes the next step materially; otherwise leave it open |

Record concise evidence and scope, not an invented personality profile. Keep private wording, uploads and reading records in local case files; the public repository can contain clearly labelled synthetic examples.

## Ask for high-information choices

Usually begin with one to three unanswered questions, selected for their impact on composition. Skip questions already answered in context. The first batch is a guide, not a mandatory form.

| Uncertainty | Useful question | Design consequence |
| --- | --- | --- |
| Main use | “主要想安排一周、记录阅读，还是观看一张主题作品？可以兼顾。” | Date, content and writing area receive different priority |
| Theme's role | “有指定的书或书单，还是先探索书页、章节等视觉语言？” | Determines whether actual book content is needed |
| Carrier | “准备挂墙、放桌面、打印书写，还是在屏幕上看？” | Viewing distance, proportion and usable writing area |
| Extent and sequence | “先做某一周，还是需要全年每周一页？” | Changes content coverage, sequence planning and validation |

Themes other than books need the same distinction: visual language, actual subject content, personal material, or an activity to record. These roles can coexist. A theme does not determine a palette, illustration style or information density by itself.

Do not turn branches into an exhaustive option tree. Resolve the largest uncertainty first. If a choice is hard to verbalize, show a small set of concrete studies and allow “combine these parts” or free-form feedback. Use [design-language.md](design-language.md) to identify which relation each study explores.

Ask for specific titles, photos, quotations, personal data or content files only when the selected direction needs them. Lack of a personal reference collection should not prevent an original design exploration.

## Separate exploration defaults from delivery facts

During exploration, a clearly labelled sample week, temporary image slot or provisional page proportion can support a visual comparison. State which choices are provisional and retain their status in the record. A placeholder is not a selected asset or completed content series.

Before describing an output as ready for its intended use, resolve the period, language, week start, carrier and necessary output dimensions from the request, established context or explicitly declared defaults. Confirm an unresolved consequential choice rather than silently treating elapsed time or absence of objection as approval. Do not ask again for information or authorization already supplied.

The system handles date calculation, source verification, font coverage, line breaks, margins, image resolution and export mechanics. Explain a technical limitation only when it changes a user's meaningful choice or the deliverable. For example, existing English-only font proofs do not establish Chinese typesetting support.

## Carry forward a compact brief

Keep the main use; viewing extent and sequence; theme and content roles; carrier; known dates/language/week start; confirmed preferences; provisional defaults; remaining questions; and any source or implementation constraints that affect the chosen direction. Use the project's case record when available; do not duplicate these facts across competing forms.

Once the next design move is clear, retrieve relevant rules and candidates from the atlas, then write the [design card](design-language.md). User choices, proposed directions and technical capability remain separate records. Questions should lead to work, not become a substitute for it.

## Short examples

**“我想要书籍主题的周历。”** This is enough to begin exploration. Treat `week` and `books` as stated clues; use and the role of books remain unknown. Ask about the highest-impact ambiguity, or show distinct concrete studies if the user requests examples first. Possible hypotheses include a chapter-like weekly page, one book as a week's content, or a reading record. None is an inferred preference, and a book list is not required for all three.

**“做一张 A4 横向中文周历，2027-04-05 到 04-11，周一开周，七天等面积，可以写笔记，用原创书籍图形。”** Proceed with the design. The period, language, carrier and central relationships are given. Select and verify suitable typography and original assets, generate exact dates and show the result. Do not restart discovery with questions about favorite books or ask the user to choose a font name.

**“如果用户说要书籍周历，我们需要哪些能力？”** Stay in discussion mode. Explain the possible roles, capability combinations and staged UX; do not treat this as an order to make a book calendar or collect the questioner's reading history.
